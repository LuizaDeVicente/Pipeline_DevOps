Primeiro, entenda o caminho.

Uma pipeline é um fluxo automatizado de tarefas. Ela transforma uma alteração de código em algo verificado e, quando as condições permitem, publicado. Pense em uma linha de produção com pontos de inspeção.

CI: verificar a mudança

A integração contínua usa verificações frequentes para detectar problemas nas alterações. Pode conferir sintaxe, executar testes e validar arquivos necessários. Uma falha deve impedir a publicação daquela execução.

CD: entregar uma versão

Neste laboratório, a implantação contínua publica automaticamente após um push na main, se a CI passar. Em outros contextos, CD também significa entrega contínua, que pode incluir uma aprovação manual.

Como o GitHub Actions organiza esse trabalho?
Workflow
Arquivo YAML em .github/workflows/ que define eventos, tarefas e condições.
Evento
O que dispara o fluxo, como um push ou um pull request direcionado à main.
Job
Um conjunto de etapas. Jobs podem executar em paralelo ou depender de outros jobs.
Step
Uma etapa de um job: executar um comando ou utilizar uma action reutilizável.
Runner
A máquina que executa o job. Não é necessário deixar seu computador ligado ao usar um runner hospedado pelo GitHub.
Checkout
Obtém o código do repositório para que o runner possa trabalhar com ele.
Artefato
Arquivos produzidos ou preparados por um job que podem ser armazenados e usados em outra etapa.
Qual é a diferença entre commit, push e pull request?

Commit registra uma versão no histórico local. Push envia commits para o repositório remoto. Pull request propõe integrar alterações de uma branch em outra. Aqui, a CI deve verificar os pull requests que têm a main como destino e os pushes na main.

Agora, construa de verdade.

Use o roteiro abaixo para implementar a automação manualmente. Este guia é a aplicação de estudo; o arquivo da pipeline será criado por você.

Antes de escolher o projeto: o enunciado pede um projeto autoral já desenvolvido e armazenado no GitHub. Confirme o enquadramento deste guia antes de adotá-lo como projeto da entrega.

  1. Entenda e versione a aplicação

    Abra esta página no navegador, explore os controles e revise o código. HTML organiza o conteúdo, CSS cuida da apresentação e JavaScript implementa as interações. Registre suas alterações no Git.

  2. Defina uma verificação útil

    Escolha o que a CI verificará: por exemplo, sintaxe do JavaScript e existência dos arquivos referenciados. Uma checagem de sintaxe não verifica o comportamento da interface; teste as interações também.

  3. Configure eventos e ambiente

    Crie seu YAML em .github/workflows/. Configure CI em push na main e pull request para main. Faça checkout e prepare as ferramentas usadas na verificação. Instale dependências apenas quando necessário.

  4. Conecte CI e CD

    Faça o job de publicação depender do sucesso da CI. Restrinja o CD a push na main. Só adicionar uma dependência entre jobs não impede a publicação em pull requests: o evento também precisa ser considerado.

  5. Escolha o destino da publicação

    GitHub Pages atende a este site estático, que não possui backend. Configure a publicação por GitHub Actions e as permissões e o ambiente exigidos pelo serviço. Publique os arquivos do site, sem incluir rascunhos do relatório.

  6. Teste os caminhos e reúna evidências

    Confira CI em pull request sem CD; push com CI e CD bem-sucedidos; e falha de validação bloqueando a publicação. Corrija a falha e confira a nova versão acessível. Registre links das execuções, commits, capturas e resultados reais.
